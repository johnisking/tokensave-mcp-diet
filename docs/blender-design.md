# Design: Blender MCP measurement and diet (draft, not started)

Status: design only, 2026-10-22. Nothing here has been measured yet.

## 1. Target

- **Primary: "MCP for Blender" (ahujasid/blender-mcp, MIT)**, about 28.7k stars. Checked at commit 5a3618f (2026-10-20). Install: `uvx mcp-for-blender`; the add-on in Blender listens on TCP 9876.
- **Phase 2: the official Blender Lab server** (GPL-3.0-or-later, Blender 5.1 or later, 26 tools). Only wrapped as a separate process, never copied, so our MIT code is unaffected.
- No public token measurements exist for either server (survey of 2026-10-22). That is the point of the dataset.

## 2. What the current server already does (read from the source)

The 2026-10 version is already careful about size, so the diet must target what is left, not what blog posts from 2025 describe.

| Tool | Result | Already limited? |
|---|---|---|
| `get_scene_info` | Text: header line plus one line per object | Yes: `limit=20`, fields chosen by the model, `query`/`root` filters |
| `look` | One PNG image (viewport, camera, several angles, or an animation strip) | Partly: `max_size` default 768 px (range 200 to 2000). Images stay in the conversation |
| `execute_blender_code` | Whatever the script prints | **No cap at all** |
| `search_assets` | Text listing, plus `previews` thumbnails (default 0) | Listing `limit=20`; each preview is another image |
| `generate_3d`, `import_asset` | Status text | Small |
| every tool | Required `user_prompt` argument: "the user's own words, quoted verbatim", on every call | Costs **output** tokens on each call; used for the server's opt-in telemetry |
| `disable_telemetry`, `record_trajectory_feedback`, `get_addon_status` | Housekeeping | Definitions only |

Claude bills an image by pixels, about width × height / 750 tokens. A 768 × 432 viewport is about 440 tokens and a 768 × 768 image about 790; both stay in every later request until the context is cleared.

## 3. Hypotheses to test

1. As with browser MCP, most of the bill is the number of steps times Claude Code's fixed per-request block, not the Blender results.
2. The big single results come from `execute_blender_code` when the model prints a lot (vertex lists, every property of many objects, long tracebacks).
3. Images add up over a long session: 10 looks at 768 px is about 4,000 to 8,000 tokens carried in every later request.
4. Repeating `user_prompt` on every call adds measurable output tokens on long build tasks.

## 4. Measurement plan (same method as dataset 20)

- Claude Code 2.1.x, Opus 5.5, effort medium, `--strict-mcp-config`, only the Blender server allowed; web, file and shell tools off.
- Blender started with the GUI (viewport capture needs it), add-on server started, fixed window size.
- **Scenes are generated by a script we write**, so they are identical every run and contain no third-party assets:
  - S (small): 12 objects, a room with a table and chairs.
  - L (large): about 600 objects, a city block of instanced buildings, plus one 200k-face mesh.
- Tasks, 5 runs each (3 for the probes):

| Id | Task | What it stresses |
|---|---|---|
| B1 | "What is in this scene and where is the camera?" on S and L | `get_scene_info` |
| B2 | "Build a low-poly table with four chairs around it" from an empty scene | many steps, code, `user_prompt` |
| B3 | "Make the chairs red and check they look right" on S | `look` images |
| B4 | "Turn the camera around the table and check each side" | several images, angles mode |
| P1 | probe: "Print the location of every vertex of the big mesh" on L | worst-case `execute_blender_code` output |
| P2 | probe: "Print every property of every object" on L | worst-case text |

- Logged per run: input, output, cache tokens, cost, requests, seconds, largest text result (chars), number of images and their pixel sizes, estimated image tokens, `user_prompt` characters sent, answered correctly (checked by a script that inspects the .blend after the run).
- About 50 runs for the baseline, then the same tasks with the diet.

## 5. Diet design (tokensave-mcp-diet 0.3, new "blender" profile)

The proxy picks a profile from the upstream tool names (browser profile for `browser_snapshot`/`take_snapshot`, blender profile for `execute_blender_code`/`look`), and keeps passing every other tool through.

1. **Text result cap (also usable for any server).** A text result over 8,000 characters is replaced by its first 2,000 and last 1,000 characters, a line count, and runs of similar lines collapsed ("498 more lines like `Vector((x, y, z))`, x from -3.2 to 4.1"). The full text is kept in memory and a new tool `result_detail(id, lines=… | grep=…)` returns any part. Tracebacks keep the last frame and the error line.
2. **Image budget.** Clamp `look`'s `max_size` to 512 unless the model asks for more than 1,000 on purpose (reading fine detail), and clamp `search_assets` `previews` to 3. Expected: a 768 px image of about 440 to 790 tokens becomes about 200 to 350.
3. **Schema trim.** Optional flag `--drop-user-prompt`: remove the `user_prompt` argument from tool schemas and descriptions, and hide the two telemetry tools. This only changes what goes to the server's opt-in telemetry; it is off by default and documented clearly.
4. **No change to `get_scene_info`.** It is already compact; we only measure it.

## 6. Risks and limits

- Blender is not installed on the test PC yet (checked 2026-10-22; GTX 1650). Installing Blender (about 400 MB) and the add-on needs the owner's OK.
- Viewport capture needs a visible Blender window; runs cannot be fully headless.
- The server changes quickly (the 2026-10 version already cut a lot). Pin the version in every log, and re-check the source before publishing.
- The server's telemetry is opt-in and off by default; leave it off during runs.
- Optional 3D-generation and asset services need their own accounts or keys; leave them out of the tasks.
- If hypothesis 1 holds and results are already small, the honest headline is "Blender MCP is lighter than its reputation; watch `execute_blender_code` output and image count", and the diet is a small add-on, not the story.

## 7. Order of work

1. Owner approves installing Blender (stable release) and the add-on on the PC.
2. Write the scene generator and the run script (reuse run_baseline.ps1).
3. Baseline runs, then decide which diet parts are worth building, based on the numbers.
4. Build 0.3, re-run, publish dataset 21 with the same page, mirrors and DOI steps as dataset 20.
